# 23 - Spring Data JPA (a second persistence style)

_Beyond the core course: add a brand-new `journal` module that talks to the database through Spring Data JPA — an interface and a Hibernate entity, zero hand-written SQL — right next to the JdbcTemplate code, so you can feel the contrast in one app._

> [!IMPORTANT]
> **Checkpoint:** [`step-23-spring-data-jpa`](../../checkpoints/step-23-spring-data-jpa/)
> — the whole Sahar app plus a new `journal` feature that uses a *different* persistence style from everything
> before it. Package is `com.ramishtaha.sahar`. In this checkpoint the journal writes are **not secured yet**
> (anyone can POST), so the `curl`s below need no login. Security lands in [step 24](./24-security.md).

## 🎯 Why this matters

Up to now every table in Sahar has been read and written with **JdbcTemplate** — Spring's thin helper where
*you* write the SQL string (`INSERT INTO ...`, `SELECT ...`) and map each row by hand. That is one honest,
widely-used style. But the Java world's most common persistence tool is **JPA** (Jakarta Persistence API),
and its everyday face is **Spring Data JPA**, where you write *no SQL and no implementation at all* — you
declare an interface and Spring generates the code.

You will meet both in real jobs, and interviewers love to ask *"JdbcTemplate or JPA — when, and why?"*. So
instead of telling you, this step lets you **hold both in the same codebase**: a new training journal built
the Spring Data way, sitting beside the JdbcTemplate repositories that run the rest of the app.

## 🧠 Theory

A few terms, defined once, then we build.

- **ORM (Object-Relational Mapping):** a library that maps rows in a table to objects in your code, so you
  manipulate objects and it generates the SQL. **Hibernate** is the most popular Java ORM.
- **JPA:** the *standard* (a set of interfaces and annotations like `@Entity`, `@Id`) that ORMs implement.
  Hibernate is the implementation Spring Boot ships by default.
- **Spring Data JPA:** a layer *on top of* JPA. Its trick: you write a **repository interface**, and at
  startup Spring creates a runtime **proxy** (an auto-generated class) that implements it for you.
- **Entity:** a plain Java class annotated `@Entity` that maps to one table. Hibernate creates instances of
  it reflectively, so an entity must be a **mutable class with a no-arg constructor** — deliberately *unlike*
  the immutable `record`s the JdbcTemplate side uses.

Here is the shape of the contrast you are adding:

```mermaid
flowchart TD
  subgraph JDBC["JdbcTemplate style (rest of Sahar)"]
    R1[record PrayerTimes] --- Repo1["repository class<br/>you write the SQL"]
  end
  subgraph JPA["Spring Data JPA style (new journal)"]
    E[@Entity JournalEntry] --- Repo2["JournalRepository<br/>(interface only)"]
    Repo2 -. Spring generates proxy .-> Hib[Hibernate]
  end
  Repo1 --> DS[(same H2 / Postgres datasource)]
  Hib --> DS
```

Same database, two doors into it. Two more ideas you must hold:

- **Flyway still owns the schema.** Hibernate *could* create tables from your entities, but we set
  `ddl-auto=validate`: on startup Hibernate only **checks** that `JournalEntry` matches the table Flyway
  built, and refuses to boot if they have drifted. Migrations remain the single source of truth.
- **The persistence context** is Hibernate's per-transaction cache of loaded entities. **open-in-view**
  keeps it open until the HTTP response is sent; we turn it **off** so it closes when the service method
  returns (more on why in the interview section).

## 🛠️ Build it

### 1. Add the starter

One dependency pulls in Spring Data JPA, Hibernate, and the transaction support — from
[`pom.xml`](../../checkpoints/step-23-spring-data-jpa/pom.xml):

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
```

It reuses the same `spring.datasource.*` Hikari pool the JdbcTemplate side already uses — no second database.

### 2. Let Flyway create the table

The schema is owned by Flyway, not Hibernate — see
[`V5__journal.sql`](../../checkpoints/step-23-spring-data-jpa/src/main/resources/db/migration/V5__journal.sql):

```sql
CREATE TABLE journal_entry (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    entry_date  DATE NOT NULL,
    energy      INT  NOT NULL,                 -- self-rated 1..5
    note        VARCHAR(1000),
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

> [!NOTE]
> `BIGINT GENERATED BY DEFAULT AS IDENTITY` is the portable SQL-standard auto-increment that works on **both**
> H2 and PostgreSQL. On the Java side it maps to `GenerationType.IDENTITY` (next step).

### 3. The entity — a mutable class, on purpose

[`JournalEntry`](../../checkpoints/step-23-spring-data-jpa/src/main/java/com/ramishtaha/sahar/journal/JournalEntry.java)
is the opposite of the immutable records elsewhere, and that is the lesson:

```java
@Entity
@Table(name = "journal_entry")
public class JournalEntry {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "entry_date", nullable = false)
    private LocalDate entryDate;

    @CreationTimestamp
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    /** Required by JPA. Not for application use. */
    protected JournalEntry() { }

    public JournalEntry(LocalDate entryDate, int energy, String note) { ... }
}
```

Why a class and not a `record`? Hibernate instantiates the entity with the **no-arg constructor**, then
fills the fields by reflection when it reads a row. Records have neither a no-arg constructor nor mutable
fields, so they cannot be entities. `@GeneratedValue(IDENTITY)` means *the database* assigns `id` on insert;
`@CreationTimestamp` lets Hibernate stamp `createdAt` on first save — you never set either by hand.

### 4. The repository — an interface, no implementation

This is the headline. From
[`JournalRepository`](../../checkpoints/step-23-spring-data-jpa/src/main/java/com/ramishtaha/sahar/journal/JournalRepository.java):

```java
public interface JournalRepository extends JpaRepository<JournalEntry, Long> {

    /** Newest first, by the day the entry is for. Query is DERIVED from this method's name. */
    List<JournalEntry> findAllByOrderByEntryDateDesc();
}
```

`JpaRepository<JournalEntry, Long>` already gives you `save`, `findById`, `findAll`, `deleteById`,
`existsById`, `count` — for free. And `findAllByOrderByEntryDateDesc()` is a **derived query**: Spring Data
*parses the method name* and writes the SQL (`select ... order by entry_date desc`). You wrote zero SQL and
zero implementation; Spring builds a proxy at startup.

### 5. The input DTO — entity ≠ request body

[`JournalForm`](../../checkpoints/step-23-spring-data-jpa/src/main/java/com/ramishtaha/sahar/journal/JournalForm.java)
is a validated `record` that is *separate* from the entity:

```java
public record JournalForm(
        @NotNull LocalDate date,
        @Min(value = 1, message = "energy is 1..5") @Max(value = 5, message = "energy is 1..5") int energy,
        @Size(max = 1000, message = "note is at most 1000 characters") String note) {
}
```

The client must not be able to set `id` or `createdAt` (those are server/database concerns), and we want Bean
Validation to reject bad input *before* it reaches Hibernate. So the request shape is its own type.

### 6. The service — the transaction boundary

Spring Data hands you a repository, yet a service still earns its place: it is where `@Transactional` lives
and where domain rules go. From
[`JournalService`](../../checkpoints/step-23-spring-data-jpa/src/main/java/com/ramishtaha/sahar/journal/JournalService.java):

```java
@Transactional(readOnly = true)
public List<JournalEntry> list() {
    return repo.findAllByOrderByEntryDateDesc();
}

@Transactional
public JournalEntry add(JournalForm form) {
    return repo.save(new JournalEntry(form.date(), form.energy(), form.note()));
}

@Transactional
public void delete(Long id) {
    if (!repo.existsById(id)) {
        throw new NotFoundException("no journal entry " + id);
    }
    repo.deleteById(id);
}
```

`@Transactional` wraps the method in a database transaction; `readOnly = true` is a hint that lets Hibernate
skip dirty-checking on pure reads.

### 7. The controller — same thin shape as the rest of the app

From
[`JournalController`](../../checkpoints/step-23-spring-data-jpa/src/main/java/com/ramishtaha/sahar/web/JournalController.java):

```java
@RestController
@RequestMapping("/api/journal")
public class JournalController {

    @GetMapping
    public List<JournalEntry> list() { return journal.list(); }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)               // 201
    public JournalEntry create(@Valid @RequestBody JournalForm form) { return journal.add(form); }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)            // 204
    public void delete(@PathVariable Long id) { journal.delete(id); }
}
```

Notice the controller looks identical in *style* to the JdbcTemplate controllers — only the machinery behind
the service changed. That is the point: the persistence choice is an internal detail.

### 8. Wire Hibernate to behave

Three lines in
[`application.properties`](../../checkpoints/step-23-spring-data-jpa/src/main/resources/application.properties)
keep Hibernate honest:

```properties
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
```

`validate` = check entities against the Flyway schema and fail fast on drift, never create/alter.
`open-in-view=false` = close the persistence context when the service returns, not at the end of the HTTP
response.

## ▶️ Try it

Start the app (`./mvnw spring-boot:run`), then — **no auth needed in this checkpoint**:

```bash
# add a journal entry -> 201 Created, with a server-assigned id + createdAt
curl -X POST localhost:8080/api/journal \
  -H "Content-Type: application/json" \
  -d "{\"date\":\"2026-06-04\",\"energy\":4,\"note\":\"good\"}"

# list entries, newest day first
curl localhost:8080/api/journal

# bad energy (outside 1..5) -> 400 with the validation message
curl -X POST localhost:8080/api/journal \
  -H "Content-Type: application/json" \
  -d "{\"date\":\"2026-06-04\",\"energy\":9,\"note\":\"too high\"}"

# delete it (use an id from the list) -> 204; deleting a missing id -> 404
curl -i -X DELETE localhost:8080/api/journal/1
```

> [!TIP]
> Open the H2 console at `http://localhost:8080/h2-console` (JDBC URL `jdbc:h2:file:./data/sahar`, user `sa`,
> no password) and run `SELECT * FROM journal_entry;` to see the rows Hibernate wrote.

> [!WARNING]
> These endpoints are unauthenticated *for now*. In [step 24 - Spring Security](./24-security.md) you will lock
> writes behind a login, so the POST/DELETE will then need `-u admin:sahar`. That is why the brief commands
> here intentionally omit credentials — they match *this* checkpoint.

## 💼 Interview angle

**Q: JdbcTemplate vs Spring Data JPA — when does each win?**
JdbcTemplate keeps you close to the SQL: you control every query, there is no hidden state, and it shines for
bespoke reads, reporting, and exact tuning — at the cost of writing CRUD boilerplate yourself. Spring Data
JPA removes that boilerplate for ordinary CRUD-shaped tables and gives you object mapping, transactions, and
derived queries — at the cost of a heavier abstraction (Hibernate, the persistence context, lazy loading,
N+1 surprises). Mature codebases often use **both deliberately**, which is exactly what Sahar now shows.

**Q: What is the N+1 select problem?**
You load N parent rows in one query, then accessing a lazy association on each parent triggers one more query
*per parent* — 1 + N queries instead of 1 or 2. It is the classic JPA performance trap. Fixes: a `JOIN FETCH`
/ `@EntityGraph` to load the association eagerly in one query, or batch fetching. (The journal has no
associations, so it can't hit N+1 — but interviewers ask anyway, because every JPA codebase eventually does.)

**Q: How do derived query methods work?**
You name a repository method following Spring Data's grammar
(`findAllByOrderByEntryDateDesc`, `findByEnergyGreaterThan`, …) and Spring **parses the name at startup** and
generates the query. No SQL, no implementation. For anything the grammar can't express you drop to `@Query`
with JPQL or native SQL.

**Q: Why can't a JPA `@Entity` be an immutable `record`?**
Hibernate needs a **no-arg constructor** to instantiate the object and then sets fields (by reflection) when
reading a row; it also wraps entities in **proxies** for lazy loading, which requires a non-final, mutable
class. Records are final, have no no-arg constructor, and expose no setters — so they can't be entities. DTOs
and value objects *should* be records; entities should not.

**Q: Why use a separate DTO (`JournalForm`) instead of binding the entity at the controller?**
The entity carries fields the client must not set (`id`, `createdAt`) and is tied to the persistence model;
binding it directly invites over-posting and leaks your schema into your API. A validated input DTO lets Bean
Validation reject bad payloads before Hibernate ever sees them, and decouples the wire format from the table.

**Q: Why `ddl-auto=validate` with Flyway, instead of letting Hibernate create the schema?**
`ddl-auto=update`/`create` makes Hibernate the de-facto schema owner — non-deterministic, no review, no rollback,
dangerous in production. With Flyway owning versioned, reviewed migrations and Hibernate set to `validate`, you
get one source of truth *and* a startup safety net: if an entity drifts from the table, the app fails fast.

**Q: What does open-in-view do, and why turn it off?**
Open-Session-In-View keeps the persistence context (and a DB connection) open for the whole HTTP request, so
lazy associations can still load while the response is being rendered. It hides N+1s, holds connections longer
under load, and lets persistence concerns leak into the web layer. Off (`false`) closes the context when the
service returns — lazy access outside a transaction then fails loudly instead of silently, which is safer.

## 🐞 Common mistakes and how to debug them

- **App won't start: `Schema-validation: missing/wrong column`** — `ddl-auto=validate` caught real drift
  between `JournalEntry` and `V5__journal.sql`. Align the `@Column` name/type with the migration (e.g.
  `entry_date` ↔ `entryDate`), don't change `ddl-auto`.
- **`LazyInitializationException`** — you touched a lazy association after the transaction closed (a natural
  consequence of `open-in-view=false`). Load what you need inside the `@Transactional` service method, or use
  `JOIN FETCH`/`@EntityGraph`. Don't "fix" it by turning open-in-view back on.
- **Tried to make the entity a `record`** — compile/boot fails. Entities must be mutable classes with a no-arg
  constructor; keep records for DTOs.
- **Derived method returns nothing or won't parse** — the method name doesn't match a property
  (`OrderByEntryDateDesc` needs a field `entryDate`). Check spelling against the entity's field names.
- **`@Transactional` seemingly ignored** — calling a `@Transactional` method from *another method in the same
  class* bypasses the Spring proxy (self-invocation). Call it through the injected bean instead.
- **Tests leak data between runs** — annotate the test `@Transactional` so each test rolls back, as
  `JournalRepositoryTest` does.
